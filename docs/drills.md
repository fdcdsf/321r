## Синтетический дрилл смены IP

Реальную смену IP у провайдера **не проводим — платная услуга** (решение 2026-11-08, PLAN v11).
Дрилл имитирует всю цепочку реального события: DNS ещё указывает на «старый» адрес → ddns сам
замечает и правит записи → соседи через reresolve переподключают пира → handshake возвращается.

«Старый» адрес = **203.0.113.10** (TEST-NET-3, зарезервирован для документации — пакеты в него
уходят в никуда, вреда нет). Если Cloudflare откажет на такой адрес — взять другой TEST-NET
(192.0.2.10 / 198.51.100.10).

### Шаг 0 — на всех трёх нодах: cron действительно запускает ddns (мгновенно)

```bash
journalctl -u cron --since "15 min ago" | grep ddns | tail -3
```

Критерий: строки `(root) CMD (/usr/local/bin/ddns.sh ...)` — по одной на каждые 2 минуты.

### Шаг 1 — нода a: «регистратор» (вкладку a не закрывать)

```bash
pe=""; pd="-"
for i in $(seq 1 14); do
  d=$(getent hosts b.321r.ru | awk '{print $1}')
  e=$(awg show wg0 | grep -A2 'peer: vHCI/H57d6v7JsIjD+iXEGdzgJEv7kkFImKasqOMHm0=' | awk '/endpoint/{print $2}')
  p=$(ping -c1 -W1 10.66.0.2 | grep -o 'time=[0-9.]*' || echo time=FAIL)
  if [ "$d" != "$pd" ] || [ "$e" != "$pe" ]; then
    printf '%s dig=%s endpoint=%s %s\n' "$(date +%T)" "${d:-нет}" "${e:-нет}" "$p"
    pd=$d; pe=$e
  fi
  sleep 15
done
echo "наблюдение завершено"
```

Печатает только моменты изменений (~3.5 мин, терминал занят — нормально). Endpoint обновляет
штатный таймер reresolve (45 с), а keepalive от b возвращает пира рокировкой (25 с) — из-за этого
endpoint и dig могут на мгновение расходиться; важно к финалу.

### Шаг 2 — нода b: имитация «IP сменился» (одна вставка, сама ждёт и снимает лог)

```bash
. /etc/ddns.env
API="https://api.cloudflare.com/client/v4"
AUTH="Authorization: Bearer $CF_TOKEN"
FAKE=203.0.113.10
ZID=$(curl -fsS -H "$AUTH" "$API/zones?name=$CF_ZONE_NAME" | jq -r '.result[0].id')
CUR=$(cat /var/lib/ddns/last_ip 2>/dev/null || true)
[ -n "$CUR" ] || CUR=$(curl -4 -fsS https://api.ipify.org)
IDA=$(curl -fsS -H "$AUTH" "$API/zones/$ZID/dns_records?type=A&name=${NODE_NAME}.${CF_ZONE_NAME}" | jq -r '.result[0].id // empty')
IDH=$(curl -fsS -H "$AUTH" "$API/zones/$ZID/dns_records?type=A&name=${HUB_NAME}.${CF_ZONE_NAME}" | jq -r --arg ip "$CUR" '.result[] | select(.content==$ip) | .id' | head -n1)
echo "CUR=$CUR IDA=$IDA IDH=$IDH"
OK=1
if [ -n "$IDA" ] && [ -n "$IDH" ]; then
  for id in "$IDA" "$IDH"; do
    if curl -fsS -H "$AUTH" -H "Content-Type: application/json" -X PATCH \
         -d "{\"type\":\"A\",\"content\":\"$FAKE\",\"ttl\":1,\"proxied\":false}" \
         "$API/zones/$ZID/dns_records/$id" | jq -e '.success' >/dev/null; then
      echo "запись $id -> $FAKE ok"
    else
      echo "ОШИБКА патча $id"; OK=0
    fi
  done
  if [ "$OK" = 1 ]; then
    echo "$FAKE" > /var/lib/ddns/last_ip
    echo "ДРИЛЛ armed: записи и состояние -> $FAKE, жду cron (<=2 мин)..."
    sleep 150
    echo "--- лог ddns:"
    tail -3 /var/log/ddns.log
  else
    echo "состояние НЕ менял — приши вывод"
  fi
else
  echo "ОШИБКА: не нашёл записи (IDA='$IDA' IDH='$IDH') — ничего не менялось"
fi
```

Порядок важен: сначала записи, потом состояние (cron между этими шагами молчит — состояние
ещё настоящее). Токен берётся из `/etc/ddns.env` на сервере и никуда не выводится.

Критерий: в логе свежая строка
`... b.321r.ru и dns.321r.ru -> 48.102.162.135` — её написал сам cron, ddns руками не запускали.

### Шаг 3 — нода a: финальная проверка (после «наблюдение завершено»)

```bash
sleep 60
getent hosts b.321r.ru
awg show wg0 | grep -A2 'peer: vHCI/H57d6v7JsIjD+iXEGdzgJEv7kkFImKasqOMHm0='
ping -c 3 10.66.0.2
```

Критерий: `48.102.162.135 b.321r.ru`; endpoint `48.102.162.135:51821`; handshake свежий;
пинг 0% потерь. Если getent ещё показывает 203.0.113.10 — кэш DNS, подождать минуту и повторить.

### Откат (если что-то пошло не так)

На ноде b, одной строкой — чинит обе записи в любом случае:

```bash
echo 203.0.113.10 > /var/lib/ddns/last_ip; /usr/local/bin/ddns.sh; echo 48.102.162.135 > /var/lib/ddns/last_ip
```

Если в шаге 2 была ОШИБКА — пришлить вывод, команда восстановления даётся отдельно.

### Что засчитывает

- Дрилл «смены IP» (PLAN, фаза 2) — цепочка ddns → DNS → reresolve → handshake без участия
  провайдера.
- Дрилл «ручная подмена A-записи» — регистратор на шаге 1 ловит переключение endpoint.
- Наблюдение за линком РФ↔зарубеж — параллельно, 1–2 дня.

### Результат (2026-11-08): оба дрилла пройдены

- b: cron сам починил обе записи на первом тике (лог 18:06:03), руками ddns не запускали.
- a: след fake→real — endpoint и пинг падали в окне ≤2 мин и восстановились; финал: настоящий IP,
  handshake свежий, 0% потерь; hub dns.321r.ru снова 3 адреса; cron подтверждён на всех трёх.
- 2026-11-09 (2-й день наблюдения): handshakes свежие на всех трёх нодах (3 с — 2 мин 32 с),
  пинг без потерь — линк РФ↔зарубеж стабилен, наблюдение закрыто.

### Ответы на вопросы по дриллу

- **Повторять дрилл нужно только с ОДНОЙ ноды** (b — «жертва», a — «регистратор»): скрипты
  и юниты на всех нодах идентичны (проверено выгрузкой с a, файлы лежат в git: scripts/,
  systemd/, cron.d/ddns). Персонального в них ничего нет — конфиги и env нод читаются на месте.
- **Принудительный `systemctl start reresolve-dns.service`** в петле не нужен: юнит — обычный
  oneshot (без RemainAfterExit), но его запуск всё равно может наткнуться на кэш NSS (`getent`),
  в то время как `dig` идёт мимо кэша — отсюда мгновенное расхождение «dig=настоящий,
  endpoint=старый». Решает всё штатный таймер 45 с.

## Дрилл промоушена PG (фаза 4, шаг 6)

### Попытка 1 (2026-11-10): НЕ пройдена — вскрыты 2 бага (ценность дрилла)

Ход: остановили контейнер первичного b → ожидаем ≤2 мин: c промоутится, метка переехала, прокси
→ 10.66.0.3, запись через VIP. Факт: флэп — c промоутился, но тут же «шаг назад» к мёртвому b,
метки разъехались, запись через VIP не проходила.

Разбор (доказательства, не гипотезы):

1. **Баг №1 (корень флэпа): `docker node update --label-remove` не существует.** Реальный флаг —
   `--label-rm`; несуществующий падал `rc=125 unknown flag`, ошибка глушилась `2>/dev/null ||
   true`. Снятие метки со старого первичного не работало НИКОГДА → после failover метка
   оставалась на мёртвом узле → чтение по порядку S находило её → «designated» возвращался к
   мёртвому. Проверено живым `--help` и ручными вызовами (оба `rc=125`). **Урок:** мок-стаб
   принимал любой флаг — харнесс доказывал логику, но не семантику docker CLI. Стаб ужесточён:
   неизвестный `--label-*` → rc=125 (как настоящий docker).
2. **Баг №2 (петля рестартов на c): `pg_wal_target_ok` читал `pg_stat_wal_receiver`.** Приёмник
   на c мёртв (таймлайн 5≠1 после повторных promote в дриле) → строка пуста → «не перевешан» →
   docker restart каждые ~12 с, который ничего не чинит, а postgresql.auto.conf рос. Исправлено:
   проверяем КОНФИГ (`SHOW primary_conninfo`) — конфиг верен → ждём, пока приёмник оживёт.
3. **Сопутствие:** c ушёл на таймлайн 5 (b = 1), стендбай с таймлайном выше не может следовать
   за первичным с таймлайном ниже; запись `_drill` ушла только в b (дивергенция). Пересборка c:
   stop → wipe `/var/lib/dbdata/pg-pangolin` + `/var/lib/pgwal/pangolin` (отдельный том!) →
   `bb.sh` (basebackup с текущего первичного) → start. Ноль потерь.
4. Мелочь: в `pg_stat_replication` колонка `state`, не `status` (опечатка в диагностике).

Исправления: `711f988` (claim: inspect-first + verify по всем нодам + до 3 попыток; шаг назад —
только при живом designated; E2/E3 тесты) и `8ba4a95` (`--label-rm`; `SHOW primary_conninfo`;
строгий стаб флагов; тесты G/G2). Мок-тесты: 61/61. Время часов: epoch нод разошёлся на 1 с
(NTP active) — «расхождение» было разницей часовых поясов (c был CET) — выправлено на UTC.

### Попытка 2 (2026-11-10, ~12:58 UTC): ПРОЙДЕНА — с двумя находками

Одним блоком с b (новый формат: первая строка — проверка ноды, удалённое — через ssh).

| Критерий | Факт |
|---|---|
| Промоушен ≤2 мин после смерти первичного | **39 с**: стоп ~12:58:20 → `ПРОМОУШЕН — c стал первичным (голосов «мёртв» ≥ кворума)` 12:58:59. **2026-11-16 (a→b): ~10 с** — ускорение после оптимизации голосов db-guard (обновление голоса при смене значения) |
| Следующий по цепи (a→b→c) | промоутился c ✓ |
| Метка: одна, у нового | debian=`c`, b — пусто (`--label-rm` в бою) ✓ |
| Прокси | все три → `10.66.0.3:5432` ✓ |
| Запись через VIP | `INSERT 0 1`, count 1→2 ✓ |
| Вернувшийся старый первичный | `СТАРЫЙ ПЕРВИЧНЫЙ b встал стендбаем → 10.66.0.3`, `pg_is_in_recovery()=t` ✓ |

Бонус: новый датчик `watch_instance` отработал в бою (`мой инстанс снова отвечает (f)` —
b поднялся как первичный на ~3 с и был шагнут в стендбай).

**Находка 1 (критично, жило с самого дня рождения): WAL-архив не работал ни на одной ноде.**
`/var/lib/pgwal/<app>` создаётся root'ом, а пишет в него postgres из контейнера →
`cp: can't create '/var/lib/pgwal/...': Permission denied` каждые секунды. Ничего не падало
(archive_mode=always терпит), но архив пуст — это ударило бы по фазе 8 (бэкапы). Вскрылось
именно сейчас, потому что на b появился файл `00000002.history` (см. находку 2) и archiver
стал его активно пробовать. Лечение: chown через образ + фикс генераторов db-add/bb.sh.

**Находка 2 (штатный случай, но с сюрпризом): b не смог вернуться стендбаем без пересборки.**
Ошибка на b: `requested starting point 0/A000000 on timeline 1 is not in this server's history
... forked from timeline 1 at 0/90000A0` + `new timeline 2 forked off ...`. То есть:
- c промоутился из точки 0x90000A0 (где прервалась репликация в момент смерти b),
- а b при подъёме «доехал» до 0xA0000A0 (на ~1 сегмент / 16 МБ вперёд — в основном служебный
  WAL: checkpoint'ы, и главное — **archiver на b копил ошибки и WAL не ротировался**, плюс
  старт-чекпоинт при подъёме) и даже породил своё ответвление timeline 2;
- старый первичный с позицией впереди точки раскола не может следовать за новым первичным —
  классика, ровно для неё в плане и есть «пересборка basebackup».

Пользовательских записей в расхождении нет (все INSERT дрила шли в c — проверено count=2).
Лечение: пересборка b с c (тот же bb-процесс, что и с c → b, но источник — c).

**Правила после попытки 2:**
1. Дрилл-блоки — всегда одним блоком, первая строка проверяет ноду, удалённое — через ssh.
2. WAL-архив: при деплое любого PG-инстанса chown каталога архива обязателен (внесено в
   db-add.sh и bb.sh).
3. Возврат старого первичного после дрила/реального отказа = пересборка (не рассчитывать на
   «сам подключится») — это ~1 минута на крошечной базе.

## Дрилл назначения Mongo (komodo, 2026-11-10): ПРОЙДЕН — с тремя находками

Механика прошла: стоп первичного mongod на b → `метка перехвачена → c` (наш скрипт, голоса
Swarm) → `ПРОМОУШЕН — RS назначил c первичным` (Mongo-выборы выполнили наше решение по
priority) — оба события за 15 с; b вернулся **SECONDARY**, c PRIMARY, a ARBITER; запись через
VIP с нейтральной ноды a прошла (count=2). Разбор «кто решает»: решение — всегда db-guard
(кворум Swarm + цепь), исполнение у Mongo — через priority + встроенные выборы (движок
нельзя заставить напрямую, но выдвигаем кандидата так, что выбор один).

**Находка 1 — VIP работал не везде:** `deploy_proxy` ставил блок прокси только на узлы
S(X); с a вне S(komodo) — `ECONNREFUSED 10.66.0.99:27017`. Нарушение «строка одинакова на
всех нодах» (PLAN §4). Исправлено: блок — на ВСЕ ноды (db-add.sh).

**Находка 2 — `docker kill -s USR1` убивал прокси:** для Docker это «остановлен
пользователем», политика unless-stopped такой контейнер не поднимает. Старый fallback
через 1 с был гонкой. Исправлено: перезагрузка прокси — `docker restart` (db-guard + db-add);
USR1 запрещён тестами.

**Находка 3 — mongosh убил базу:** `docker exec mongod-... mongosh` выполняется в том же
memcg (300M), mongod ~214M + mongosh ~100M → OOM-киллер снёс **mongod** (rc=137,
restarts=2). Исправлено: mem_limit mongo → 512M (db-add.sh); правило: руками mongosh —
только отдельным контейнером `docker run --rm --network host mongo:7 mongosh ...`.

## Дрилл фенсинга (2026-11-10): ПРОЙДЕН

Симуляция «РКН отрезал ноду c» (iptables OUTPUT DROP трафика c→a,b, ssh оставлен для
наблюдения) — по сценарию A2 плана:

| Критерий | Факт |
|---|---|
| Изоляция → фенс ≤2 мин | **57 с** (`ФЕНС: нет кворума Swarm дольше 60 с`) ✓ |
| DROP в DOCKER-USER | 3 правила на позициях 1–3 (mesh + локальный путь) ✓ |
| Большинство работает и пишет | a промоутился на **72-й с**, `INSERT` через VIP прошёл ✓ |
| Возврат линии → фенс снят ≤2 мин | **44 с** (`ФЕНС снят: кворум Swarm восстановлен`) ✓ |
| Старый первичный встаёт стендбаем | `СТАРЫЙ ПЕРВИЧНЫЙ c встал стендбаем → 10.66.0.1` ✓ |
| Стендбай догоняет | через пересборку (закономерность ниже) ✓ |

**Наблюдение 1 (полезное):** кворум Swarm после возврата линии не мгновенный — Raft
пересобирается ~1 мин. Фенс снимается только когда кворум подтверждён (правильно — лучше
перебдеть), но проверять «ФЕНС снят» надо через пару минут, не через 30 с.

**Наблюдение 2 (закономерность, подтверждена ВТОРОЙ раз):** вернувшийся старый первичный не
может стать стендбаем без пересборки — его журнал уехал вперёд точки раскола
(`requested starting point 0/C000000 on timeline 2 is not in this server's history ...
forked from timeline 2 at 0/B000168`). То же было с b после дрила промоушена. Правило:
**возврат старого первичного после изоляции/остановки = пересборка basebackup (~1 мин)** —
штатное лечение, не авария. После пересборки: c — `t`, `streaming`, `_drill=3`; на a две
реплики; прокси везде `10.66.0.1:5432`.

| Критерий | Факт |

оба: `systemctl stop docker.socket docker`.

подряд (c: «метка перехвачена» 18:12:38 → b: «RS назначил b» 18:12:56). Гонка кандидатов
сошлась к консистентному состоянию (метка = RS-первичный) без вмешательства — db-guard
самоизлечивается. Приёмлемо.

## Фаза 5: находки развёртывания Pangolin (ночь 2026-11-10/11)

**Находка 1 (правило файрвола — было в комментарии, но споткнулись):** DOCKER-USER считает
**контейнерные** порты (после DNAT). Публикация `8443:3000` блокировалась снаружи и из mesh,
т.к. `3000` нет в белом списке PUBLIC_TCP — а локальные curl через docker-proxy давали 200
(он мимо DOCKER-USER). Правило: при маппинге `host:container` сверять с таблицей §3 по порту
**контейнера**. Лечено переносом entrypoint дашборда на `:2053` (есть в таблице).

**Находка 2 (архитектурная): HTTP-01 невозможен при multi-A.** Let's Encrypt (multi-VA,
2025+) проверяет **все** A-записи имени; challenge существует только на ноде-заявителе —
чужие ноды отвечают 404 → выдача никогда не пройдёт. Решение: **DNS-01** (traefik +
`dnsChallenge.provider: cloudflare`, токен — тот же, что у ddns, `/etc/ddns.env`). Коллизия
TXT-записей при одновременной выдаче на 3 нодах («Incorrect TXT record») лечится повтором.
Итог: сертификаты `pangolin.321r.ru` выданы на все три ноды (2026-11-11, ~21:05–21:08 UTC).

**Находка 3 (масштабирования):** раскатка «профильная» — один скрипт `node_rollout.sh`
(параметры по hostname) отрабатывает любую ноду; секреты рендерятся из `/etc/db/secrets/`
на месте, в git — только шаблоны `deploy/pangolin/*.tmpl`.

## Дриллы фазы 9 и ресурсных профилей (2026-11-16)

### «VPS-2 лёжит» (панель Remnawave недоступна) — ПРОЙДЕН

Стоп `remnawave` + `remnawave-subscription-page` на b. Результат: **все маски VPN
(vpn-a/b/c) и tg остались 200**, Xray-ноды running на всех нодах, логи remnanode спокойны.
Деградация — только `rem.321r.ru` → 503 (нет новых подписок/изменений — ожидаемо,
VPN живёт по закешированному конфигу). Возврат: панель снова 200 за **~30 с**.

### Смерть панели Pangolin (cgroup-OOM профиля S) — ПРОЙДЕН

`pkill -9 server.mjs` в контейнере панели на a. **Ingress ноды не заметил**: komodo via a = 200
во время дауна (gerbil держит туннели), маска Xray независима. Панель поднялась за **~5 с**.
Вывод: cgroup-OOM панели валит только дашборд — трафик не страдает (требование V1/20 ✓).

### «IP одной ноды заблокирован» — ПРОЙДЕН (с двумя методологическими находками!)

Симуляция: DROP на a (443/2087) → `tg.321r.ru via a` = 000 (счётчики тикают), `via b/c` = 200,
ресурсы/дашборд через живые ноды = 200. Внешняя проверка с машины владельца — то же самое.
Клиенты с multi-A конфигами продолжают работать через две оставшиеся ноды ✓.

**Находка 1 (напоминание + усиление правила фазы 5):** DNAT на PREROUTING **переписывает порт
на контейнерный** (host 443 → контейнер 8443) ДО цепочки DOCKER-USER. Правило `DROP dpt:443`
в DOCKER-USER никогда не сработает — надо `DROP dpt:8443`. А host-порты без маппинга
(2087, 8446, 2099 — host-сеть) живут в INPUT. Проверять блокировку — **по счётчикам пакетов**
(`iptables -L -v`), а не по «мне кажется, должно быть».

**Находка 2 (грабли):** `ufw delete <rule-spec>` матчится по порту и **удалил не то правило**
(вместо несуществующего deny — наш allow 443!). Правило: удалять только по номеру —
`ufw status numbered` → `ufw delete N`. Правило 443 восстановлено.

### «Панель ×1 + gerbil по mesh» (профиль M) — ЧАСТИЧНО ПРОЙДЕН, есть ТЗ инсталлятору

Переключение gerbil на a: `--remoteConfig=http://10.66.0.2:3001/api/v1/` + стоп локальной панели.
Результат: **логика есть** — gerbil реально ищет конфиг по mesh
(`Fetching remote config from http://10.66.0.2:3001/api/v1/gerbil/get-config`), но получил HTML:
порт 3001 на b — это Kuma-ingress, а **API панели опубликован только на 127.0.0.1**.
Без конфига gerbil = весь ingress ноды мёртв (даже tg-маска: traefik живёт в netns gerbil).

**ТЗ инсталлятору (профиль M/S):**
1. Публиковать API панели на mesh: `10.66.0.X:3000:3000` (не только 127.0.0.1).
2. Порядок восстановления: **сначала здоровая панель, потом gerbil/traefik**
   (сейчас подтверждено: gerbil без конфига убивает ingress ноды).
3. `depends_on: pangolin: service_healthy` в compose мешает режиму «панель вовне» —
   для профилей S/M нужен compose-вариант без этой зависимости (`--no-deps` — только костыль).

Возврат после дрилла: стек восстановлен (komodo/дашборд/tg via a = 200), бэкап compose
применён, gerbil снова смотрит на локальную панель.

## Живая миграция и «Потеря большинства» (2026-11-17)

### app-move: перенос члена БД-группы — ПРОЙДЕН (нулевой даунтайм)

`app-move.sh remnawave b a`: подготовка инстанса на a (secrets+compose) → копия данных
штатным `pg-rebuild-standby` (basebackup через VIP) → смена placement `[b,c]→[a,c]` на всех
нодах → вывод старого инстанса (данные остаются до ручной очистки). Итог: a=standby
(streaming), c=PRIMARY, панели не заметили ничего. Первичный едет через `--claim-now`
(промоушен цели + перенос метки + проверка VIP).

### Дрилл «Потеря большинства» (2 из 3 нод лежат) — ПРОЙДЕН

Фазы: стоп docker на a+c (штатный способ из V1/13) → **ФЕНС на выжившей b через 60 с**
(как задумано) → решение владельца `survival.sh` (= `/survival` в боте) → фенс снят,
выжившие сервисы работают: дашборд 200, маски vpn-b/tg 200, mongo force-reconfig ok →
возврат нод → **«КВОРУМ ВОССТАНОВЛЕН, шаг назад»** → все роли сошлись автоматически
(pangolin b=PRIMARY, komodo b=PRIMARY, remnawave c=PRIMARY; standbays переподключились
сами — conninfo через VIP). Метрики: фенс 60 с; выживание — сразу после команды владельца;
полное восстановление — ~90 с после возврата нод.

**Уроки дрилла:**
1. **Выживание работает только для инстансов, живущих на выжившей ноде.** Группа remnawave
   `[a,c]` целиком легла → панель 503 до возврата нод (или восстановления из 3-2-1!).
   Правило: критичные данные — минимум одна копия на ноде из failure-домена выживания.
2. **Предохранитель вырос до v3 за один дрилл:** v1 «psql без пароля» → ложное «первичного
   нет» (split-brain!); v2 «tcp_ok до VIP» → фантом: haproxy принимает хендшейк всегда,
   даже с мёртвым бэкендом. **v3 (финал): протокольная проверка psql с паролем из secrets
   + fail-safe по rec=t.** Проверять живость — только на уровне протокола приложения!
3. Mongo пережил и аварию, и возврат: force-reconfig не сломал конфиг — a и c вернулись
   в RS сами.
4. db-guard в тишине не спамит: события легли в Telegram ровно по делу (фенс, метка,
   промоушен, возврат).
5. **Ложный фейловер под нагрузкой** (2026-11-17: тестовый трафик заставил tcp-проверку
   моргнуть → remnawave «переехал» на a): одна неудачная проверка не повод объявлять смерть.
   В db-guard введён **анти-флэп**: голос «мёртв» — только после 2 подряд неудачных проверок
   (~20 с). Цена: фейловер на ~20 с медленнее, зато без ложных срабатываний.
