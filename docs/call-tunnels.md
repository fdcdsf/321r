# Туннели через звонки: оценка для 321r (2026-11-20)

**Статус: исследование архитектуры, на наших VPS не устанавливалось и в сети
с «белыми списками» не проверялось.** Ни одна схема не гарантирует доступность:
операторы и платформы могут менять правила, CAPTCHA, лимиты и адреса.

## Что подходит нам

**Да, возможен отдельный ОПЦИОНАЛЬНЫЙ модуль** рядом с обычным Remnawave:

1. На `a`, `b`, `c` — свои независимые creator-сессии и локальные процессы;
   закрепить за каждым его исходящий IP, **не переносить** на другую ноду при
   падении. Не использовать Pangolin multi-A для медиатрафика и не смешивать
   эти сессии с WG-мешем кластера.
2. В 321r-боте: «создать звонок для устройства» → выбрать ноду/платформу →
   запустить creator по запросу → дождаться готовой ссылки → показать/отозвать.
   Ограничить число активных сессий и память (одна сессия ≠ множество устройств),
   подтверждать остановку чужой сессии. Меню и состояние динамические по нодам.
3. Страница на Яндекс CDN — **канал доставки ссылок и инструкций**, если она
   действительно открывается при конкретном белом списке. Сам VPN-трафик CDN
   **не переносит**: после открытия страницы устройство должно соединиться
   с API/TURN/SFU платформы звонка. Публичный CDN-кеш не подходит для выдачи
   активных ссылок без контроля доступа; сначала проверять модель авторизации,
   TTL, cache-control и риск утечки ссылки. Без неё выдавать ссылки лично через
   бот, а на странице публиковать только инструкцию и кнопку запроса.
4. Это **не** `tg://proxy` и не стандартная `vless://`-подписка: нужен
   совместимый joiner (Android/iOS/desktop или локальный клиент+WG). Для
   `vk-turn-proxy -vless` интеграция с нашим Xray :9446 — отдельный PoC, не
   считать её доказанной из одного наличия флага в коде.

**Первый PoC уточнён после выбора клиента владельца:** сначала iOS/SRTP,
как описано ниже. `whitelist-bypass` (headless creator на одной VPS + свой
joiner Android/desktop, DC/Video) — отдельный второй эксперимент, который
**не** проверяет совместимость с его iPhone-приложением. В обоих случаях
измерять RSS/CPU, задержку, доступность из сети с белым списком, расход
трафика, реальный IP, восстановление и необходимость ручной CAPTCHA.

**Предохранители:** не заявлять «работает при любых белых списках» до полевого
теста из нужной сети; не публиковать учётные cookies/VK-токены/открытые
ссылки звонков в git; ограничить доступ через firewall и по возможности
внутреннюю аутентификацию WG/VLESS; без проверки допустимой нагрузки на
сторонний сервис не масштабировать одновременно сотни звонков.

## Реальный клиент владельца: iOS SRTP + проверка с ПК

Владелец использует `anton48/vk-turn-proxy-ios`. В его
[`docs/setup.md`](https://github.com/anton48/vk-turn-proxy-ios/blob/main/docs/setup.md)
указано: по умолчанию **SRTP**, а исходный `cacggghp/vk-turn-proxy` понимает
только более медленный **Legacy**. Значит сначала ставить совместимый
[`anton48/vk-turn-proxy`](https://github.com/anton48/vk-turn-proxy) с `-srtp`.

1. **Одна расходная VPS:** отдельный UDP listener (например :56000) и
   отдельный WG-инстанс на локальном порту/подсети; **не** использовать
   кластерный `wg0` и занятый Gerbil :51820. Выход — через публичный IP
   этой VPS, без переноса peer на соседние ноды. Релиз сервера
   `srtp-build478` заявлен совместимым с iOS `v1.0-build486` (в примечании
   к iOS-релизу: «server stays srtp-build478»); версию установленного
   приложения надо сверить перед тестом.
2. **Телефон:** режим SRTP и отдельный WG peer. Скрипт автора
   [`quick_link.py`](https://github.com/anton48/vk-turn-proxy-ios/blob/main/quick_link.py)
   формирует `vkturnproxy://import?...` и соответствующий серверный `[Peer]`.
   Импортная ссылка содержит **приватный ключ WG в base64**. Её отдавать
   владельцу адресно через Telegram-бота, а не выкладывать в открытый CDN.
3. **ПК пользователя — Windows:** у автора есть
   [`vk-turn-proxy-console`](https://github.com/anton48/vk-turn-proxy-ios/blob/main/docs/console.md)
   с **тем же SRTP-транспортом**, но релизы сейчас только Linux/macOS/FreeBSD.
   Для честного теста на Windows-ПК подойдёт небольшая **Linux VM**; консоль
   создаёт TUN и меняет маршруты/DNS **внутри VM**, не на VPS кластера.
   Она читает экспорт iOS-приложения; для одновременного подключения телефона
   и VM нужны **два разных WG peer и IP**. Одну резервную копию с одним
   приватным ключом нельзя использовать одновременно: peer-и столкнутся.
   Windows-клиент исходного `cacggghp` тестирует Legacy, не SRTP — результат
   по скорости/совместимости будет непоказателен. WSL2 без проверки TUN и
   маршрутизации Windows не считать полноценным PC-тестом.
4. **Яндекс CDN:** страница может показывать инструкцию и ссылки на VK-звонки,
   но не пропускает TURN/SRTP и не заменяет импорт с WG-ключом. Если VK
   звонки публичны, есть риск занять их квоту посторонними. Нужна проверка
   доступа и кеша; персональный `vkturnproxy://` на публичной странице нельзя.

После полевого PoC бот: выбор ноды `a/b/c`, добавление отдельного WG peer,
выдача личной импортной ссылки, статистика и удаление peer с подтверждением.
Это **другая модель**, чем `whitelist-bypass`: не нужен отдельный creator
на каждого клиента, но ограничения/квоты соединений VK TURN всё равно есть.
