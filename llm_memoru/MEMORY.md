## 1. Рабочий режим (нарушать нельзя)

1. **Модель готовит команды, пользователь вставляет и присылает вывод.** Полная вставка —
   только для исходников файлов, которые идут в git (их модель пишет сама, файлами).

   Файл `C:\Users\user\AppData\Roaming\sops\age\keys.txt` — не печатать даже частично.
3. **Доставка на ноды — SFTP** (репозиторий приватный, ноды pull не умеют). Скрипты — в git,
   на ноды через SFTP + `scp -P 2222` между нодами по mesh.
4. **Крупные вставки — кусками ~50 строк** с проверками `wc -l` / `bash -n` / md5.
5. **Патчи и мок-тесты — локально ДО выкладки.** Харнесс `tests/run_db_guard.sh` (71/71) доказывает
   логику, но НЕ семантику docker CLI — флаги проверять по живому `--help` (урок бага №1 ниже).
6. Вывод пользователя иногда обрезается — при сомнениях переспрашивать свежей командой.
7. Объяснения — по-русски, простым языком, с аналогиями. Скорость важнее церемоний, но
   порядок шагов PLAN — контракт.

**Изменение режима (2026-11-10, решение владельца):** владелец передал модели SSH-ключ для
прямой работы с нодами («серверы будут удалены после готового продукта»). Теперь модель

## 3. Архитектура БД (v14 — суть)

- **PG/Mongo — «глупые исполнители» воли Swarm.** БД(X) живёт ТОЛЬКО на узлах S(X) из
  `apps.d/<app>.yaml`; placement БД = S(X) точно; per-node сервисы свои БД не реплицируют.
- **DCS = Docker Swarm** (метки `db-primary-<app>`, Raft, placement). Этим заняты голоса
  `vote.<app>.<alias>=<0|1>-<epoch>` (свежесть 45 с), кворум ⌊M/2⌋+1, цепь S(X) a→b→c.
- **Адрес для приложения — вечно статичный:** `10.66.0.99:<порт>`. За ним локальный haproxy на
  каждой ноде → текущий первичный. Приложение никогда не перепривязывается.
- **PG:** async streaming primary/standby (один инстанс = одно приложение); promote через
  `pg_ctl promote`; старый первичный шагает назад (standby.signal). **Mongo:** RS, но первичный
  назначается скриптом (priority 1 назначенному, 0 остальным; force-reconfig без первичного).
- **db-guard** (systemd-timer 5 с на каждой ноде, `/usr/local/bin/db-guard.sh`):
  healthcheck TCP → голоса → кворум → promote + claim метки + перевешивание прокси →
  шаг назад старого первичного → **фенс: нет кворума >60 с → 3 DROP в DOCKER-USER (позиция 1)**.
  Нет кворума → выйти до решений (CP). Метка `db-primary-<app>` живёт ТОЛЬКО на узле первичного.
- Классы: кластерный (|S|≥2) / локальный / служебный (арбитры). Mongo |S|=2 → арбитр на 3-м узле.
- Новое приложение: запись в `apps.d/` + `scripts/db-add.sh` — само (basebackup/-R, RS, метки, proxy).

### Находки ночного развёртывания Pangolin (2026-11-10/11)
- **DOCKER-USER считает КОНТЕЙНЕРНЫЕ порты (после DNAT)** — это было в комментарии скрипта,

  на несколько нод невозможен: challenge живёт только на ноде-заявителе, чужие отвечают 404.

- PowerShell: `curl` — это Invoke-WebRequest (нужен `curl.exe`), а `$` в `bash -c "..."`
  съедается PowerShell. Сложные команды — только файлами.
- **API Komodo (`/auth/login/...`, порт 9120) и Pangolin (`/api/v1/...`, порт 8443) — разные
  продукты с разными API**; не путать (обе ошибки были).

### Находки Pangolin — дни 2 (2026-11-11, «битва за nov.321r.ru»)
- **ИТОГ (ИСПРАВЛЕНО!): второй уровень nov.321r.ru РАБОТАЕТ** (nov6 = 200 со всех трёх нод,
  сертификат `*.321r.ru, 321r.ru` от LE). Ранний вывод «не маршрутизируется» был неверным:
  404 давало отсутствие сертификата, а не маршрутизация. **Причина — 3 бага Pangolin v2.3.4:**
  (1) `createOrder` добавляет `*.` к уже wildcard-домену → LE отказывает (`*.*.base`);
  (2) в `dnsRecords.value` пишется плейсхолдер «Server IP Address» → валидация никогда не
  проходит; (3) `failed`-сертификаты не переиздаются, `clear-certificates` сносит и валидные.
  **Лечение:** `scripts/pangolin-wildcard-repair.sh <IP>` (SQL: `*.base`→`base` в certificates,
  плейсхолдер→реальный IP, сброс failed). Запускать после каждого рестарта pangolin (таймер).
  Полный рецепт для установщика (DNS, конфиги, одна ACME-нода, `_acme-challenge.<base>` NS):
  **docs/pangolin-wildcard.md**. CNAME-домены — запасной путь, не основной.
- **cert_resolver обязателен** (дока wild-card-domains): домен из config.yml должен иметь
  `cert_resolver: "letsencrypt"` + `prefer_wildcard_cert: true`, и в traefik-секции конфига
  те же дефолты — иначе сертификаты пытается выдавать сам Pangolin (его DNS-валидация с
  плейсхолдером «Server IP Address» не проходит никогда → домен «отваливается» → ресурсы
  не создать). Добавлено (40fc2cf). Токен CF подходит тот же (Zone:Read+DNS:Edit) —
  env-алиас CLOUDFLARE_DNS_API_TOKEN дописан в traefik-cf.env.
- **Wildcard-сертификаты** (`*.app.321r.ru`) у NS-зон работают автоматически уже сейчас.
- **Управляемые конфигом домены** (`domains:` в config.yml + `disable_config_managed_domains:
  false`) заводятся с verified=true БЕЗ DNS-валидации. Валидация ручных доменов сравнивает
  `resolved.includes(record.value)`, но value = плейсхолдер «Server IP Address» (панель
  подставляет IP инстанции при показе!) — проходит никогда. Мульти-A проходит по includes.
- **Сетевая ловушка compose**: traefik с `network_mode: service:gerbil` — при рестарте
  gerbil ПЕРЕСОЗДАВАТЬ и traefik (docker compose up -d --force-recreate gerbil traefik),
  иначе traefik в осиротевшем netns → всё обрывается (000/EOF). Одиночный `docker restart`
  запрещён!
- **API Pangolin** (веб-морду не трогать — работает через API с сессией из браузера):
  CSRF-заголовок `X-CSRF-Token: x-csrf-protection` (статическая строка).
  Маршруты: `PUT /api/v1/org/{org}/domain` (создание домена), `DELETE .../domain/{id}`,
  `PUT /api/v1/org/{org}/resource` (создание ресурса: name, subdomain, domainId, mode),
  `PUT /api/v1/resource/{id}/target` (цель: siteId, ip, port, hc*), `POST /api/v1/target/{id}`
  (обновление цели), `GET /api/v1/resource/{id}/targets`, `GET/DELETE .../dns-records`.
- Маршрутизация ресурсов: gerbil → `get-resolved-hostname` (эндпоинты туннелей) → Newt.
  Нездоровая цель (hcHealth=unhealthy) НЕ маршрутизируется (фильтр в resolveExitNodes).
- DNS сделано: `*.321r.ru` A ×3 + `321r.ru` A ×3 (все IP, multi-A живучесть), NS-делегирование
  `_acme-challenge.321r.ru → dns.321r.ru` (для wildcard-сертификатов через DNS-01).
  Зона `app.321r.ru` (NS) — рабочий образец. Решение за владельцем: скрипт-обёртка /
  жить в зоне / полная делегация зоны (стать своим DNS через reg.ru).
