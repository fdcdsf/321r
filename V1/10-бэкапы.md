## Правила (приняты владельцем)

1. **Последний бэкап — на 2 соседние настраиваемые ноды** (не одна!).
2. **Недельные и более старшие копии — со сжатием** и выбором хранилища (куда — настраивается).
3. Облачных хранилищ (R2 и т.п.) **нет** — только свои VPS по мешу + GitHub для конфигов.
4. Секреты бэкапов (пароль restic) — SOPS + **распечатка** (офлайн).
5. Правило «нет единственных копий» — бэкапы это подстраховка от логических ошибок
   (плохой DELETE применяется мгновенно, бэкап — нет), а не основной способ хранения.

Аналогия: бэкап — это не «второй дом», а страховка от того, что вы сами залили воду на пол:
кластер держит копии железа, бэкап держит копию «прошлого».

## Цепочка копий (кто кому шлёт)

```text
домашний сервер ──► VPS-1 (a) ──► VPS-2 (b)      домашние сервисы, Newt
                        │
                        └──► VPS-3 (c)            WAL-архив и дампы всех БД (bulk, 4TB)
VPS-2 ──► VPS-3 (дубль restic) и GitHub (конфиги)
MongoDB панелей ──► VPS-1 и VPS-3                 дампы каждые 30–60 мин
```

С учётом блокировок: линк РФ↔зарубеж может рваться — VPS-1 (РФ) копии принимает и держит.

## Что делается автоматически (расписание)

| Что | Куда | Как часто | Ретеншн |
|---|---|---|---|
| WAL каждого PG-инстанса | `/var/lib/pgwal/` + VPS-3 | каждые 5 мин | 7 дней |
| pg_dump/mongodump всех инстансов | VPS-3 | ежесуточно | 14 дней |
| restic: критичное (конфиги, секреты-enc) | VPS-1 → VPS-2 | еженедельно | по политике |
| restic: bulk (домашнее) | → VPS-3 | ежесуточно | по политике |
| Дампы MongoDB панелей (Remnawave, Komodo) | → VPS-1, VPS-3 | 30–60 мин | 14 дней |

**Уже работает на стенде:** локальный WAL-архив на всех нодах, mongodump/restore проверены.
**Фаза 8 сделает:** выгрузку на соседние ноды по правилу «2 копии», restic-репозитории,
сжатие недельных, Telegram-отчёты о свежести.

## Восстановление: сценарии

### 1. Логическая ошибка (плохой DELETE / битый апдейт)

```bash
# найти нужный дамп на бэкап-ноде, восстановить в песочницу, потом в базу:
docker run --rm --network host -v /var/lib/pgbackup:/b postgres pg_restore ...
# Mongo:
docker run --rm --network host -v /var/lib/pgbackup:/b mongo:7 mongorestore ...
```

### 2. Потерян один сервер (все данные на других копиях)

Бэкап нужен только как страховка — в основном данные догоняются репликацией:
новая нода → `db-add` (basebackup/rs.add): [07-замена-сервера](07-замена-сервера.md).

### 3. Потеряны ВСЕ узлы с данными («ракета в датацентр»)

```bash
bash cluster.sh up inventory.yaml        # новый кластер ~1 час
bash cluster.sh restore --from <бэкап>   # базы: base+WAL или дампы
```

RTO: часы (зависит от объёма). RPO: последние секунды/минуты (по расписанию дампов).

### 4. Восстановление PG с точностью до секунды (PITR)

База + WAL-архив: `pg_basebackup` → наложение WAL до нужного момента.
Рецепт — в PLAN.md §4 (пункт 7, заготовка); автоматизация — фаза 8.

## Проверка бэкапов (это самое важное!)

- **Бэкап без проверки — не бバックап.** Раз в квартал — дрилл восстановления на временную
  VPS ([17-дриллы](17-дриллы.md)): развернуть из копий и убедиться, что данные на месте.
- Еженедельно: смотреть логи бэкапов (фаза 8: автоматический отчёт в Telegram со статусом
  «свежесть/размер/последняя успешная копия»).
- Алерт о «залежавшемся» бэкапе (>24 ч без свежего) — часть мониторинга
  ([11-мониторинг](11-мониторинг.md)).
