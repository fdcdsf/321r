# 21 — Доктрина 321 и дизайн фазы 8

Обновлено: 2026-11-16. См. также: [20-ресурсы-и-профили](20-ресурсы-и-профили.md),
[10-бэкапы](10-бэкапы.md), [11-мониторинг](11-мониторинг.md), `PLAN.md` §Фаза 8.

> **Проект называется 321r — в честь правила бэкапирования 3-2-1.** Фаза 8 — та самая,
> где правило становится механикой продукта. Главные требования: **минимум потребления
> ресурсов** (бюджет V1/20) и **отказоустойчивость** по формуле N = 2K+1, с выживанием
> и при потере большинства (с честной ценой).

## 1. Правило 3-2-1 → механика

| Правило | Трактовка продукта |
|---|---|
| **3** копии | живая реплика в кластере + бэкап на соседних нодах + выгрузка на физический носитель |
| **2** носителя | ноды территориально разнесены и у разных провайдеров (своя гео/железо) + физический диск владельца |
| **1** offsite | физический носитель владельца (через Telegram-выгрузку); ключ SOPS — распечатка офлайн |

**Топология бэкапов (решение владельца 2026-11-16):** бэкапы каждой ноды лежат на **двух
других** нодах (ноды 1 → на 2 и 3; ноды 2 → на 1 и 3; ноды 3 → на 1 и 2). Для N=2K+1
обобщение: копии каждой ноды — минимум на 2 других узлах из **разных failure-доменов**
(провайдер/гео). Плюс периодическая выгрузка через Telegram-бота на физический носитель
(ритуал раз в месяц; см. §3).

## 2. Отказоустойчивость: N = 2K+1 и лестница деградации

| Потеряно | Режим | Цена |
|---|---|---|
| ≤ K (1 из 3, 2 из 5, 10 из 21) | **полная функция** — кворум, консистентность, RPO ≈ 0 | нет |
| > K, но данные выжили | **«аварийный режим»** — выживший принудительно поднимается | потеря последних транзакций, риск split-brain при возврате «мёртвых», громкие предупреждения |
| почти всё | **остаточное выживание** — VPN/туннели по кешу, доступны копии 3-2-1 | восстановление из бэкапов, RTO ~1 ч |

**Аварийный режим — включение через Telegram-бота** (решение владельца): при потере
кворума бот шлёт алерт с кнопкой «[Поднять аварийный режим]» — владелец подтверждает.
Опционально в `cluster.yml` — `survival.auto_after: 30m` для необслуживаемых установок.

**Правило возврата (обязательно!):** при оживлении «мёртвых» нод НИКАКОГО авто-слияния —
сверка таймлайнов, правило «шаг назад», стендбаи восстанавливаются штатным
`pg-rebuild-standby.sh` (уроки 2026-11-13). Аварийный старт всегда оставляет громкое
событие в журнале и в алертах.

## 3. Telegram-бот — единый канал: управление + алерты + транспорт бэкапов

Один компонент, три роли (решение владельца 2026-11-16):

1. **Управление:** панель на кнопках с вложенными меню (v3, 2026-11-17): 📊 Статус,
   🟢 Сервисы, 💾 Бэкапы, 🗄 Базы, 🖥 Серверы (по нодам: статус/диски/контейнеры/логи/перезапуск),
   📜 Логи, ⚙ Действия (бэкап/верификация/выгрузка/аварийный режим). Опасные действия —
   только через экран подтверждения (кнопки ✅/❌). Текстовые команды работают как алиасы.
   Факты с нод собирает `tg-info.sh` (status|disk|db|backup|certs|services|app <имя>).
   **Карточки приложений** (🧩): Pangolin / Remnawave / Komodo / mtproto — здоровье точек,
   где живёт, роли БД, компоненты, логи и перезапуск; **🧩 Инстансы БД — топология
   кнопками**: перенос (app-move.sh), добавление/удаление члена (app-member.sh).
   **Авто-открытие (2026-11-17):** всё живое видно БЕЗ настройки — контейнеры
   (`docker ps`), swarm-сервисы (`docker service ls`), базы (по /var/lib/dbdata),
   ноды (cluster.yml); раздел «📦 Контейнеры и сервисы». Карточки-группы — редактируемый
   файл `/etc/db/bot-apps.yml` (перечитывается при показе; правки видны сразу).
   **Автоматика:** дозор `tg-watch.sh` (каждый час на всех нодах; алерт только при проблеме:
   диск/RAM/load/сертификаты <14 дн/бэкап/верификация) + утренний дайджест `tg-digest.sh`
   (09:00: статус нод + проблемы, «всё ок» одной строкой).
2. **Алерты и мониторинг:** протухание бэкапов (маяки), события db-guard (ПРОМОУШЕН,
   ФЕНС, аварийный режим), health-checkи сервисов. Kuma — опционально, не обязателен.
3. **Транспорт offsite:** выгрузка бэкапа владельцу в чат → запись на физический носитель.

**Факты Telegram (Bot API, core.telegram.org):** обычный бот — файлы до **50 МБ**;
локальный Bot API server — до **2000 МБ**. Схема выгрузки: архив нарезается кусками
~45 МБ (`split`), бот шлёт частями, владелец склеивает (`cat parts > archive`); шифрование
— встроенное (restic) или пароль архива. Никаких секретов в чат — только шифротекст.

**Дёшево и цензуроустойчиво:** long-polling (только исходящие соединения — никаких открытых
портов!), ~30–50 МБ RAM, в профиле S — на одной ноде. **HA:** инстанс бота на каждой ноде,
но алерты/команды отправляет «говорящий» = держатель метки `db-primary-control`
(при её смене бот подхватывает) — дубли исключены, выжившая нода достучится.

**Безопасность:** whitelist chat_id владельца; опасные операции — только с кнопкой
подтверждения; токен бота — в `/etc/db/secrets/` (umask 077), в git не попадает.

## 4. Манифест кластера `cluster.yml` (прозрачность и редактируемость)

Единый человекочитаемый файл (на нодах в `/etc/db/`, копия в git) — источник правды
о составе серверов и размещении (решение владельца 2026-11-16):

```yaml
cluster: 321r
servers:                       # ← прозрачный редактируемый список
  - {name: a, ip: 178.236.242.213, geo: ru, provider: vps1, size: s}
  - {name: b, ip: 48.102.162.135,  geo: de, provider: vps2, size: m}
  - {name: c, ip: 194.48.141.214,  geo: de, provider: vps3, size: m}
apps:                          # требования, а не жёсткие ноды!
  - {name: pangolin,  engine: pg,    replicas: 3, rule: 321}
  - {name: remnawave, engine: pg,    replicas: 2, rule: 321}
  - {name: komodo,    engine: mongo, replicas: 2, arbiter: 1, rule: 321}
backup: {on: 2-other-domains, retention: {daily: 30, weekly: 12, monthly: 12}, export: telegram-monthly}
survival: {policy: manual-via-bot, auto_after: null}
```

- Приложения описывают **требования** («3 реплики в 2 доменах»), движок сам выбирает ноды.
- `cluster apply` — приводит реальность в соответствие манифесту (reconciliation):
  добавили сервер → приложения доехали; удаляем сервер → сначала переселение (`app move`).
- Манифест версионируется в git = история изменений кластера.

## 5. Живая миграция приложений (`app move` — без значимого выключения)

**Управление инстансами — через Telegram (🧩 Инстансы в карточке приложения):**
перенести / добавить / убрать инстанс БД кнопками с подтверждением (движки:
`app-move.sh` — перенос, `app-member.sh add|remove` — члены группы). Защита:
нельзя убрать последний инстанс и первичного (сначала перенос). Источник правды
о занятости — placement; остаточные данные после переноса помечаются и перезаливаются.

Козырь: приложения не знают, где БД (VIP + db-guard). Паттерны:

| Тип | Как | Даунтайм |
|---|---|---|
| БД-кластер (pg/mongo) | новый член на целевой ноде → синхронизация → плановый промоушен (**~10 с, дрилл**) → вывод старого | секунды |
| Stateless (панели, subpage) | поднять на новой → перевесить трафик → остановить старую | ~0–30 с |
| Singleton (valkey, mongo local) | поднять новый → переключить потребителей → бросить старый | секунды–минута |

Порядок восстановления из дриллов соблюдается (панель → gerbil), каждый шаг — с проверками
и откатом.

## 6. Верификация и дриллы («бэкап, который не восстанавливали, не существует»)

- **Автовосстановление-тест** раз в неделю: scratch-инстанс из свежего бэкапа + smoke-проверки.
- **Маяки свежести:** бэкап-джоб пишет heartbeat; «протух > 2 интервалов» → алерт в бота.
- **Квартальные дриллы:** полное восстановление из offsite-копии (RTO ~1 ч — меряем!),
  «потеря большинства» (аварийный режим по кнопке), миграция `app move`.
- Метрики — в [17-дриллы](17-дриллы.md) и `docs/drills.md`.
