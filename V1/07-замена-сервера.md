# 07 — Замена сервера: IP, блокировки, потери, апгрейд железа

Обновлено: 2026-11-12. См. также: [05-добавление](05-добавление-ноды.md),
[06-удаление](06-удаление-ноды.md), [13-эксплуатация-и-отказы](13-эксплуатация-и-отказы.md).

Четыре разных случая, которые часто путают. Первые два сервер вообще не меняют.

## Случай 1. IP сервера сменился (провайдер)

**Это несобытие** — автоматика чинит за ≤3 минуты, руками ничего:

1. `ddns.sh` (cron 2 мин) правит A-записи `<alias>` и свою строку в `dns.321r.ru`.
2. `reresolve-dns.sh` (таймер 45 сек) переподключает пиров меша к новому IP.
3. `update-pangolin-ips.sh` (вызывается из ddns) правит `trusted-upstreams`/`base_endpoint`.

Проверить после: `wg show` — handshake свежий; `curl https://pangolin.321r.ru/` = 200.
Дрилл «синтетическая смена IP» пройден 2026-11-08 (см. `docs/drills.md`).

## Случай 2. IP заблокировали (РКН или хостер)

**Симптомы:** из РФ не открываются дашборд/ресурсы по этому IP (другие IP из multi-A —
открываются); пинги/хендшейки к ноде из РФ не идут; из-за рубежа всё работает.

**Что происходит само:** браузеры перебирают IP из multi-A — вход идёт через незаблокированные
ноды; **РФ-ноду (a) блокировать нечем** — она и есть гарантированный вход
([01-обзор](01-обзор-проекта.md), п.5). Newt/агенты сайтов сами уходят на живые ноды (секунды).

**Что делать человеку (по нарастанию):**

1. Убедиться, что всё ещё доступно через остальные IP:
   `curl -sk --resolve pangolin.321r.ru:443:<живой-ip> https://pangolin.321r.ru/`.
2. Потребовать у провайдера смену IP → дальше случай 1 (автоматика).
3. Если провайдер не меняет — **заказать новый сервер**, перенести роль (случай 3/4).
4. Резервные пути (план Б): запасные порты дашборда 8443/2053; для людей — VPN-слой
   Remnawave (фаза 9) обходит любые блокировки; zapret на домашнем роутере; третий
   вариант транспорта меша — xray-туннель (`docs/amnezia-wg.md`).

**Если РКН начнёт резать протокол (не IP):** AmneziaWG → обычный WireGuard → xray-туннель
(порядок деградации из плана; рецепты — `docs/amnezia-wg.md`).

## Случай 3. Сервер потерян (ракета, неуплата, сгорел диск) — замена новым

Цель: **новая VPS вместо старой за ~1 час**, данные догоняются сами. RPO — секунды
(асинхронная репликация), если потерян один узел из многих.

### Быстрый путь (одной командой, проект фазы 10)

```bash
bash cluster.sh replace --alias c --ip <новый-ip> inventory.yaml
```

### Пошагово

1. **Убрать мёртвое тело**: `docker node rm --force <старое-имя>` на живой менеджерской;
   вычистить упоминания по шагу 3 [06-удаления](06-удаление-ноды.md)
   (★ nodes.map на всех, apps.d, trusted-upstreams, сайт-агент).
   DNS-записи НЕ удалять — они переедут на новый сервер.
2. **Новая VPS** (та же юрисдикция/роль предпочтительно): запустить bootstrap
   ([04-развёртывание](04-развёртывание-с-нуля.md)) с **тем же alias и mesh-IP** —
   система считает её «вернувшимся домом».
3. **DNS**: A-запись `<alias>.321r.ru` → новый IP (ddns сделает и будет поддерживать);
   строка в `dns.321r.ru` — переписать на новый IP.
4. **Swarm**: join менеджером (токен с живой ноды); метка роли.
5. **Данные**: `db-add.sh <app>` для каждого приложения с alias ∈ S(X) —
   стендбай через `pg_basebackup`, Mongo через `rs.add` — **данные догоняются сами**.
   Если была первичной — db-guard уже назначил другую (≤2 мин); вернувшаяся станет стендбаем.
6. **Pangolin**: поднять стек, **обязательно** `pangolin-wildcard-repair.sh <новый-ip>`;
   создать сайт-агент `cluster-<alias>` заново (старые учётные данные удалены в шаге 1).
7. **Komodo**: periphery + onboarding-key.
8. **Если погибла ACME-нода** (у нас b): включить `enable_acme_client` на одной из живых
   нод (только на одной!) и перезапустить её pangolin — сертификаты живут в PostgreSQL
   и восстановятся сами.
9. Приёмка: автопроверки S9 ([04](04-развёртывание-с-нуля.md)).

### Сколько занимает

| Шаг | Время |
|---|---|
| bootstrap ноды | 10–20 мин |
| swarm join + метки | 2 мин |
| db-add (basebackup/rs.add) | 5–15 мин (по объёму БД) |
| Pangolin + repair + агент | 10 мин |
| проверки | 5 мин |
| **Итого** | **~1 час** |

## Случай 4. Плановая замена железа (старый сервер жив)

Самый безопасный: **переезд роли, а не инцидент**.

1. Добавить новый сервер как ноду ([05-добавление](05-добавление-ноды.md)) — кластер растёт.
2. Перевести на неё роли старой:
   - БД: расширить S(X) на новый узел → `db-add` (догонит) → сузить S(X) со старого
     (db-add пересоберётся; для Mongo `rs.remove`);
   - метки/роли Swarm переставить; ACME-роль — если была на старой;
   - сайт-агент: пересоздать на новой ноде (или оставить оба временно).
3. Убрать старый сервер по [06-удаление](06-удаление-ноды.md).
4. DNS: постепенно переставить A-запись на новый IP (ddns подхватит).

Окно недоступности — ноль: кластер работает всё время, DNS переключается на лету.

## Какой случай у вас? (дерево решений)

```text
Сервер отвечает, но IP другой?        → случай 1 (ничего делать, ждать ≤3 мин)
Из РФ не идёт, из-за рубежа идёт?     → случай 2 (блокировка)
Сервер молчит совсем?                 → случай 3 (потеря → замена)
Хотите переехать на лучшее железо?    → случай 4 (плановая замена)
```

## Таблица «кто что чинит сам»

| Событие | Автоматика | Человек |
|---|---|---|
| Смена IP | ddns + reresolve + update-pangolin-ips (≤3 мин) | ничего |
| Блокировка одного IP | multi-A перебор, уход туннелей | смена IP у провайдера / новая VPS |
| Потеря одного сервера | Swarm переносит задачи, db-guard назначает первичного, кластер жив на N−1 | поставить новую VPS (случай 3) |
| Потеря двух серверов | фенсинг (данные целы), но кворума нет | аварийное восстановление: [13-отказы](13-эксплуатация-и-отказы.md), сценарий D |
