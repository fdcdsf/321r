Обновлено: 2026-11-12. См. также: [03-факты](03-факты.md), [15-требования](15-требования-к-инсталлятору.md).

## Принципы

1. Наружу открыто ровно то, что должно работать (таблица портов — [03-факты](03-факты.md)).
2. Меш (10.66.0.0/24) — доверенная зона; всё остальное — default deny.
3. Секреты не бывают «немножко в утечке»: утёк — считаем скомпрометированным.
4. Человеческий фактор закрывается 2FA и recovery-кодами офлайн.

## SSH

- Порт **2222**, только ключи: `PasswordAuthentication no`, `PermitRootLogin prohibit-password`,
  `KbdInteractiveAuthentication no`, `MaxAuthTries 3`.
- Порядок при настройке (урок прошлой ошибки!): **сначала подтвердить ключевой вход, потом
  закрывать пароль.** Иначе можно остаться без доступа.
- fail2ban: jail `sshd`, порт 2222, ignoreip = localhost + 10.66.0.0/24, 3 попытки → бан 1 ч.
  Разбан: `fail2ban-client set sshd unbanip <ip>`.
- Матрица SSH «все на всех» проверяется после каждого изменения (по 2222, ключи).

## Firewall (ufw, default deny)

- Открыто наружу: 80/443/8443/2053/2222 tcp + 53(udp, rate-limit 30/с)/51820/21820/51821 udp.
- Mesh: `ufw allow from 10.66.0.0/24` — одно правило, доверенная зона.
- Зона контейнеров: ufw-правила от 172.16.0.0/12 и 10.0.0.0/8 на порты БД 5432:5499 и
  27017:27099 (ставит `db-prep.sh`; при выходе порта за диапазон — дописать).

## DOCKER-USER (классическая ловушка!)

Docker публикует порты **мимо ufw** — фильтрует только цепочка `DOCKER-USER`.
Наша политика: публичные порты §3 — пропустить, остальным — DROP (последнее правило).

**Ловушка (наступили дважды):** DOCKER-USER видит пакеты ПОСЛЕ DNAT — порт здесь
**контейнерный**, а не host-маппинг! Публикация `8443:3000` блокировалась, потому что в белом
списке был `8443`, а виден `3000`. Сверять по порту контейнера.

**Фенсинг использует эту же цепочку**: 3 DROP-правила вставляются в позицию 1 при потере
кворума (изоляция ноды). Внимание: `docker-user.sh` при перезапуске **СТИРАЕТ** правила
фенса — при ручных работах помнить об этом.

## Секреты

| Правило | Детали |
|---|---|
| Никогда в чат и никогда в git | открытые секреты в репозитории — нет; аудит 2026-11-10 подтверждён |
| Генерируются на нодах | `umask 077` → `/etc/db/secrets/*.env`, chmod 600 |
| В git — только зашифрованные | SOPS (age), `secrets/*.enc.yaml`; ключ age — `%APPDATA%\sops\age\keys.txt`, **в менеджер паролей + печать** |
| Вывод с секретами маскировать | `sed "s/[A-Za-z0-9_-]\{20,\}/СКРЫТ/g"` перед показом |
| Ротация | CF-токен уже ротировался (2026-11-09); HPK меша ротировать при утечке дампа |

**Известный компромисс (осознанный):** SSH-ключ стенда проходил через чат — считается
скомпрометированным; **серверы стенда будут уничтожены после готового продукта**.
Для публичного релиза (фаза 10): новый ключ, новая история git.

## Сетевые принципы безопасности

- Из РФ идём только на свои VPS (принцип 5 плана) — не тащим секреты через заблокированные
  сервисы.
- Адреса БД (VIP 10.66.0.99) — приватный диапазон, наружу недостижим, в меш не
  маршрутизируется (каждая нода отдаёт его только своим контейнерам).
- Mongo без авторизации — осознанно (только mesh); при выходе за пределы mesh — ставить
  авторизацию.
- Порты панелей наружу не выносим: UI — только через ресурсы Pangolin (HTTPS + свои
  сертификаты).
