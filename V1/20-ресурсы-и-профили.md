# 20 — Ресурсы и профили (бюджет продукта)

Обновлено: 2026-11-16. См. также: [03-факты](03-факты.md), [15-требования-к-инсталлятору](15-требования-к-инсталлятору.md).

> **Зачем этот файл.** Продукт — не для нашего стенда. Конечный пользователь может иметь
> три сервера по 1 ядру/2 ГБ, а то и по 1 ГБ. Значит, у продукта должен быть **честный
> бюджет памяти** и **профили**, под которые он укладывается. Все цифры ниже — ИЗМЕРЕНЫ
> на стенде 2026-11-16 (RSS в установившемся режиме, после прогрева).

## 2. Правила бюджета (вшиваются в продукт, не «на всякий случай»)

1. **У каждого контейнера есть `mem_limit`.** cgroup-OOM убивает контейнер (он перезапустится),
   а не роняет ноду. Для Node.js — ещё и `NODE_OPTIONS=--max-old-space-size`.
2. **Потолок кучи Node.js обязателен:** панель Remnawave из коробки ставит
   `--max-old-space-size=16384` (16 ГБ!) — на слабой ноде это путь к OOM всей машины.
   Экономия от капа скромная (−35…−100 МБ), но **безопасность — главная причина**.
3. **Кэш WiredTiger mongo НЕ ужимать ниже 0.25** (mongo не стартует: `BadValue`).
   Поэтому mongo — самый «дорогой» необязательный компонент; на слабых нодах его либо
   не ставим, либо одним инстансом (`class: local`).
4. **Никаких тяжёлых форков в циклах** (mongosh = 200 МБ пик; docker CLI тоже не бесплатен).
5. **journald ограничен** (`SystemMaxUse=200M`) — иначе за неделю сотни МБ диска и I/O.
6. **Тяжёлое — на большие ноды, или вовне кластера** (см. профили).

## 3. Профили

### Профиль S — минимум (ноды 1 vCPU / 1–2 ГБ)

| Компонент | Решение |
|---|---|
| Меш + слой БД + вход (gerbil/traefik) + Xray-ноды | **обязательно на всех нодах** |
| Панель Pangolin | **вне кластера**: `--panel=connect:<url>` (домашний сервер, старый VPS, ноутбук-мини) — режим из фазы 9! |
| Панель Remnawave | на самой большой ноде (440 МБ) или тоже `--panel=connect` |
| Komodo + mongo | `--komodo=no` (управление через CLI/ssh) или mongo `class: local` одной нодой |
| Kuma | `--kuma=no` (внешние проверки, например UptimeRobot) |
| mtproto | опционально (+13 МБ — дёшево) |

Бюджет ноды: ОС 250 + gerbil/traefik 80 + PG 25–70 + db-proxy 50 + Xray 110 + mtproto 13
≈ **530–570 МБ** → укладывается в 1 ГБ. Рекомендация: swap 512 МБ как подушка всплесков.
Нода с панелью Remnawave: +440 МБ → этой ноде нужно ≥ 2 ГБ (или панель тоже вовне).

### Профиль M — средний (ноды ≥ 2 ГБ, одна ≥ 4 ГБ)

- `--panel=install`: панель Pangolin **×1 на самой большой ноде**; gerbil остальных нод
  смотрит на неё по mesh (`--remoteConfig=http://10.66.0.X:3001/api/v1/`) — **спроектировано,
  требует дрилл-проверки** (fallback: панель ×3, если RAM позволяет).
- mongo `class: local` одной нодой (Komodo есть, но без RS) — или RS, если все ноды ≥ 2 ГБ.
- Kuma на одной ноде.

### Профиль L — всё включено (как наш стенд: 2/8 + 4/4 + 1/2 ГБ)

Всё, что есть: панель Pangolin ×3 (HA дашборда), mongo RS (b,c + арбитр), панель Remnawave
+ подписка, Kuma, Komodo, mtproto. Пиковая нода (b) ≈ 2.9 ГБ — подтверждено замерами.

## 4. Честные минимальные требования (для README продукта)

| Конфигурация | Минимум железа |
|---|---|
| Ядро кластера (меш + БД + вход + VPN), панель вовне | **3 × (1 vCPU, 1 ГБ)**, swap 512 МБ рекомендуется |
| + панель Remnawave на VPS | нода панели ≥ 2 ГБ |
| + Komodo (mongo) | ноды mongo ≥ 2 ГБ (пол кэша WT) |
| Всё сразу (профиль L) | как минимум одна нода ≥ 4 ГБ |

## 5. Что проверить дриллом (открытые пункты дизайна)

1. **Панель ×1 + gerbil по mesh** (профиль M): переживает ли ingress работу без локальной
   панели (связь gerbil→remoteConfig), как быстро восстанавливается после возврата.
2. **cgroup-OOM панели** (профиль S, нода 1 ГБ): панель под капом не должна вредить трафику
   (gerbil/Xray продолжают работать, панель просто перезапускается).
3. Замер «после месяца работы»: рост RSS (утечки Node.js) — кап кучи их не лечит.
