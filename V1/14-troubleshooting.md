# 14 — Troubleshooting: ищем по симптому

Обновлено: 2026-11-12. См. также: [16-api-и-команды](16-api-и-команды.md),
`docs/pangolin-wildcard.md`, `docs/drills.md` (протоколы инцидентов).

Формат: **симптом → вероятная причина → лечение**. Все случаи ниже — реальные, со стенда.

## Веб-ресурсы Pangolin

### «404 page not found» на ресурсе

Три разных причины с одной маской (случай proxmox.321r.ru, 2026-11-12):

1. **Цель unhealthy → маршрутизатор отсекает её.** Health-check цели создан неполным
   (UI-мастер!) или не настроен вовсе. → Полный набор HC-полей через API
   (`POST /api/v1/target/{id}`: hcEnabled, hcPath '/', hcScheme, hcMode, hcHostname,
   hcPort, hcInterval 5, hcUnhealthyInterval 30, hcTimeout 5, hcMethod GET,
   hcFollowRedirects). Внимание: цель БЕЗ строки HC тоже отсекается (SQL NULL ≠ 'unhealthy').
2. **Агент (Newt/CLI) со старым конфигом** — после удаления/пересоздания ресурсов он живёт
   старым списком целей до sync. → Перезапуск агента на клиенте или смена секрета сайта
   (агент переподключится и подтянет конфиг).
3. **Маршруты между нодами не сошлись** (туннель держит одна нода, другие пересылают;
   после ребутов сходимость 1–2 мин). → Подождать или перезапустить gerbil на «отстающей».

Признак различия: `000`/таймаут через одну ноду — почти всегда случай 3.

### «503 no available server» (traefik)

За туннелем никто не слушает порт цели: агент не подключён, порт цели мёртв, или агент с
устаревшим internalPort. → Проверить сайт в панели (online?), лог агента на клиенте
(`Sync: adding TCP target ...`), HC цели.

### Сертификат «TRAEFIK DEFAULT CERT», ресурсы 404

Баги Pangolin v2.3.4 (двойная `*.`, плейсхолдер «Server IP Address», залипший `failed`). →
`pangolin-wildcard-repair.sh <ip>`; после каждого рестарта pangolin. Подробно —
[08-домены](08-домены-и-сертификаты.md).

### «Domain is not verified» при создании ресурса

Тот же плейсхолдер в `dnsRecords.value` (баг 2). → repair-скрипт; для config-доменов
(`domains:` в config.yml) валидация не нужна — `verified=true` сразу.

### Работает через один IP, не работает через другой

Кросс-маршрутизация/здоровье цели. Проверка по IP: `curl -sk --resolve <имя>:443:<ip> https://<имя>/`.
→ Смотреть HC цели и сходимость маршрутов (случай 3 выше).

### traefik/gerbil: 000 или EOF после рестартов

traefik живёт в `network_mode: service:gerbil` — одиночный `docker restart gerbil` оставляет
traefik в осиротевшем netns. → `docker compose up -d --force-recreate gerbil traefik`
(только вместе!).

## Базы данных

### «read-only transaction» при записи в PG

Вы пишете в стендбай. → Только через VIP `10.66.0.99:<порт>` (он ведёт на первичного).

### `FATAL: requested timeline N is not a child of this server's history` (краш-цикл)

Штатный случай после ребут-шторма: диск стендбая отстал. → `pg-rebuild-standby.sh [app]`
на больном узле (~1 мин, сам найдёт первичного через VIP).

### `FATAL: remaining connection slots are reserved`

`max_connections` мал (было 20). → Норма 200 (исправлено в `db-add.sh`); для живого
инстанса — правка конфига + рестарт в окно.

### Контейнер «жив, но мёртв» (unhealthy, рестарта нет)

Docker перезапускает только ПАДШИЕ контейнеры. → `unhealthy-restart.sh` (cron каждую минуту)
уже лечит; вручную: `docker restart <имя>`.

### Mongo молчит / «сел по памяти»

`mongosh` внутри контейнера mongod убивал базу по OOM. → Только отдельным контейнером:
`docker run --rm --network host mongo:7 mongosh ...`. mem_limit mongod — 512M (300M мало).

### Прокси не переключился после промоушена

Перезагрузить прокси правильно: `docker restart` (НЕ `docker kill -s USR1` — это «остановлен»).

### db-guard молчит о проблеме / что делает

`journalctl -t db-guard -n 30 --no-pager`; маркеры: ПРОМОУШЕН, метка перехвачена, ФЕНС…

## Меш и сеть

### Пир меша не поднимается

1) DNS имя endpoint'а резолвится в старый IP → reresolve (45 с) или `reresolve-dns.sh wg0`;
2) HPK (HeaderProtectionKey) различается между нодами — обфускация не сходится;
3) модуль `amneziawg` не загружен (`dkms status`, `modprobe amneziawg`);
4) не тот порт (меш — 51821, gerbil — 51820).

### Сервис недоступен из мира, из mesh — работает

DOCKER-USER режет публикацию (порт контейнерный!) или ufw. → Сверить `iptables -L DOCKER-USER`
с портом КОНТЕЙНЕРА; помнить про фенс-правила (позиция 1) и что `docker-user.sh` их стирает.

### Из РФ не открывается, из-за рубежа — открывается

Блокировка IP. → [07-замена-сервера](07-замена-сервера.md), случай 2; вход через РФ-ноду
и запасные порты 8443/2053.

## SSH и доступ

### Забанен fail2ban

`fail2ban-client set sshd unbanip <ip>` (с другого адреса/по консоли провайдера).
Игнор-лист: localhost + 10.66.0.0/24.

### Остался только парольный доступ / потеряны ключи

Консоль провайдера → `authorized_keys` вручную. Правило: сначала подтверждаем ключевой вход,
потом отключаем пароль.

## Pangolin/панели

### После правки БД pangolin «откатил» изменения

Синхронизация при старте пересоздаёт записи из конфига (плейсхолдер dnsRecords). → Не
рестартовать pangolin после ручной правки; repair-cron долечит.

### Команда `pangctl clear-certificates` удалила хорошие сертификаты

Известная особенность (сносит все строки). → Перевыпуск через repair; не использовать без нужды.

### Агент на клиенте не синхронизируется

Лог агента: искать `Sync:`/`Websocket connected`. → Рестарт агента / смена секрета сайта
(учётные данные в панели Sites).

## Быстрая диагностика «в одной вставке»

```bash
# снаружи (с рабочей машины), по всем IP:
for ip in <ip1> <ip2> <ip3>; do
  curl -sk --connect-timeout 6 --resolve <имя>:443:$ip https://<имя>/ -o /dev/null -w "via $ip: %{http_code}\n"
done
# на ноде:
docker ps --format '{{.Names}}\t{{.Status}}' | sort
journalctl -t db-guard -n 10 --no-pager
wg show | grep -E 'peer|latest handshake'
```

## Панель Pangolin работает «через раз», ресурсы пропадают/не отображаются

- **Симптом:** дашборд открывается не всегда; ресурсы эпизодически 404/503 или «исчезают».
  В логе панели: `57P03 cannot_connect_now`, `Failed to fetch active domains from traefik config`.
- **Причина:** переключение первичного PostgreSQL (db-guard промоутил другую ноду) — панель
  в момент смены получает 57P03 и **не может построить traefik-конфиг** → ресурсы пропадают.
  Частый спутник: старый первичный не может вернуться стендбаем («timeline N is not a child»).
- **Лечение (штатное, ~1 мин):** `pg-rebuild-standby.sh pangolin` на кашляющей ноде → в логе
  «started streaming WAL ... on timeline N». Проверка: 57P03 нет, `pg_stat_replication` полон.
- **Профилактика:** `journalctl -t db-guard` (маркеры «инстанс не отвечает», «ПРОМОУШЕН»);
  после переключения БД — 1–2 мин на сходимость и проверка панели.
- Инцидент 2026-11-13: первичный мигал (FATAL «in recovery mode» при promote), b ушёл в
  timeline-петлю → панель «через раз», ресурсы не отображались. Вылечено пересборкой.
- **Дополнено 2026-11-16 (полная цепочка инцидента).** Пустые списки — верхушка айсберга:
  1) запрос списка ресурсов панели деградировал до **10+ секунд** (монстр-план с JIT и
  битой статистикой: план оценивал 1 трлн строк на таблицах из единиц) → панель отменяла
  его по таймауту (**57014** `query_canceled`) → UI молча показывал «Результаты не найдены»;
  2) на ноде с PG (a, 1 vCPU, нагрузка ~7) память контейнера pg-pangolin упёрлась в
  `mem_limit 200m` → **cgroup OOM-киллер убил postgres-бэкенд** (видно в `dmesg`) →
  crash-recovery PG (~2 с недоступности) → все панели получали **57P03** на мёртвых сокетах.
  **Лечение:** `ALTER DATABASE pangolin SET jit = off;` + `ANALYZE;` (запрос: 10.7 с → 20 мс!),
  `docker update --memory 512m pg-pangolin` на всех нодах, перезапуск панелей (сброс пулов).
  **Профилактика:** jit=off и mem_limit 512m вшиты в `db-add.sh`; `ANALYZE` после крупных
  правок БД руками; следить за `uptime` слабых нод; смотреть `dmesg | grep -i oom`.
- **Known issue (2026-11-16) — ЗАКРЫТ: PG-первичный мигрирован a → b** стандартным
  промоушен-дриллом (стоп pg на a → db-guard назначил b за ~10 с → a пересобран стендбаем,
  реплики streaming). Тяжёлые запросы панелей теперь исполняются на b (2 vCPU/8GB).
  Приёмка: VIP → PRIMARY b, haproxy-апстрим 10.66.0.2, панель отвечает на всех трёх нодах.
- **Симптом: нагрузка (load) 4–5 при видимом простое, ядро ест CPU без пользы.**
  Причина 2026-11-16: наши же проверки — `mongosh` (Node.js, старт ~1–2 с CPU) каждые 5 с
  × несколько вызовов + `docker node update` на каждый тик + логи mongo на 1.5 ГБ.
  Диагностика: `top -bn2 | head`, `vmstat 1 3` (столбцы us/sy/wa), `du -h
  /var/lib/docker/containers/*/*-json.log`. Лечение: кешированные проверки в db-guard
  (см. `scripts/db-guard.sh`), тик 10 с, logrotate, `vm.swappiness=10`.
  Проверка: load падает в течение 5–15 минут.
- **Симптом: в `/var/log/ddns.log` «ddns: не удалось узнать свой IP», A-записи не
  обновляются.** Причина 2026-11-16: все три внешних сервиса определения IP (ipify,
  ifconfig.me, ip-api.com) стали недоступны — ddns падал на первом шаге молча.
  Лечение: в `ddns.sh` добавлен фолбэк — IP берётся с интерфейса (docker-подсети
  отфильтрованы). Проверка: прогон `bash /usr/local/bin/ddns.sh` молчит (rc=0).
- **Симптом: маскировка «светится» — порт 8446 (mtproto) открыт наружу.** Проверка:
  `ufw status | grep 8446` — правило `8446/tcp ALLOW Anywhere` быть НЕ должно
  (должно быть только `8446 ALLOW 172.16.0.0/12`). Лечение: `ufw delete allow 8446/tcp`
  (сделано на стенде 2026-11-16; mtbuddy после переустановки может добавить снова — проверять!).
- **Симптом: `mongod` входит в crash-loop, в логе «Error during global initialization …
  BadValue … cacheSizeGB».** Причина: **MongoDB не принимает `wiredTigerCacheSizeGB` меньше
  0.25** — попытка ужать кэш арбитра до 0.1 кладёт контейнер. Лечение: вернуть 0.256;
  экономить на mongo можно только `mem_limit` (арбитру — 300m, проверено: ~126 МБ usage).
